# 收入合同详情页界面重构设计

## 1. 文档目的

本文定义收入合同详情页的目标信息架构、统一应收事件口径、按合同类型切换的主视图，以及现有数据模型需要补齐的能力。

本次重构的核心不是为不同合同类型复制多套详情页，而是把合同执行过程统一投影为可展示、可汇总、可追溯的应收事件：

> 某个合同项或订单，在一个确定日期或满足某个条件后，应收多少钱；目前已形成应收多少、已开票多少、已分配回款多少、尚欠多少、是否逾期，以及计划为什么发生变化。

## 2. 系统边界

详情页继续遵循经营台账定位：

- 合同、合同项、计费规则和计费分段是计费依据。
- 已确认应收明细是经营应收事实。
- 有效发票映射是合同侧已开票事实。
- 有效回款分配是合同侧已收款和经营核销事实。
- 未分配银行流水不归属某一份合同，不计入合同详情页“已收款”。
- 法定账、税务、坏账审批、资金账户余额仍不在本插件中处理。

界面可以展示外部系统已经确认的调整结果，但如果要解释调整类型、发生日期和原因，需要增加可追溯数据结构。仅有 `adjusted_amount` 不能满足差异解释要求。

## 3. 设计原则

### 3.1 一个详情页，多种业务视图

保留一个收入合同详情入口。页面顶部、综合时间轴、关联抽屉和明细表共用；中间主视图根据合同类型选择：

| 合同类型 | 默认主视图 | 辅助视图 |
| --- | --- | --- |
| 周期性 | 周期账单矩阵 | 综合时间轴、年度日历 |
| 阶段性 | 里程碑时间线 | 综合时间轴 |
| 框架 | 订单/开工单泳道 | 额度概览、综合时间轴 |
| 订单 | 订单履约泳道 | 综合时间轴 |
| 混合 | 多收费计划泳道 | 周期矩阵、里程碑时间线 |

现有“全链路版、可视化运营版、领导审查版”不再作为三份独立模板维护。管理视角通过页面密度、默认折叠状态和视图标签表达。

### 3.2 时间轴为主、日历为辅、明细表兜底

- 时间轴回答“什么时候应收、目前走到哪一步”。
- 专属主视图回答“钱由哪些月份、阶段、订单或收费计划产生”。
- 日历回答“应收集中在哪些日期”。
- 明细表负责筛选、导出、审计和财务核对。

### 3.3 不伪造日期

未来事件必须区分：

1. `fixed_date`：已经确定具体日期。
2. `trigger_offset`：触发条件确定，但触发日期未知，例如“验收后30日”。
3. `estimated_date`：有当前预测日期，但仍具有不确定性。

未触发的条件型事件显示“待验收触发 → 触发后30天到期”，不得使用合同项生效日代替计划到期日。

### 3.4 金额和状态必须可追溯

顶部卡片、主视图、抽屉和明细表必须使用同一套聚合服务。缓存字段只能用于性能优化和对账，不能与明细实时汇总形成两套互相矛盾的展示口径。

## 4. 统一应收事件

### 4.1 定位

`ReceivableEvent` 首先作为只读展示投影，不要求第一阶段立即增加单表。它可以由合同项、计费规则、计费分段、应收明细、发票映射和回款分配组合生成。

当现有模型无法表达计划版本、条件日期或订单状态时，再补充源模型，而不是把所有字段堆入投影缓存表。

### 4.2 建议字段

| 分组 | 字段 | 说明 |
| --- | --- | --- |
| 标识 | `event_key` | 稳定、唯一，可用于抽屉定位和前端交互 |
| 标识 | `contract_id` | 收入合同 |
| 标识 | `project_id` | 项目，可为空 |
| 标识 | `order_id` | 订单/开工单，可为空 |
| 标识 | `contract_line_id` | 合同项 |
| 标识 | `billing_rule_id` | 计费规则 |
| 分类 | `event_type` | recurring、milestone、one_time、adjustment |
| 分类 | `charge_item` | 收费项目名称 |
| 分类 | `billing_period` | 周期事件的账期 |
| 触发 | `trigger_type` | fixed_date、trigger_offset、estimated_date |
| 触发 | `trigger_event` | 验收、交付、开通等 |
| 触发 | `offset_days` | 触发后多少天到期 |
| 日期 | `original_planned_date` | 合同签订时原计划日期 |
| 日期 | `current_planned_date` | 当前预计日期，可为空 |
| 日期 | `actual_trigger_date` | 实际触发日期，可为空 |
| 日期 | `receivable_date` | 实际形成应收日期，可为空 |
| 日期 | `due_date` | 实际到期日；未触发时可为空 |
| 金额 | `original_planned_amount` | 原始合同计划金额 |
| 金额 | `current_planned_amount` | 当前计划金额 |
| 金额 | `receivable_amount` | 已确认应收净额 |
| 金额 | `invoiced_amount` | 有效发票映射金额 |
| 金额 | `received_amount` | 有效回款分配金额 |
| 金额 | `adjustment_amount` | 已确认调整净额 |
| 金额 | `uninvoiced_amount` | 已形成应收减已开票 |
| 金额 | `unreceived_amount` | 已形成应收减已分配回款 |
| 状态 | `receivable_status` | 未触发、待确认、已形成、已作废 |
| 状态 | `collection_status` | 未开票、已开票、部分回款、已结清、逾期 |
| 状态 | `uncertainty_level` | 确定、预计、待触发 |
| 解释 | `adjustment_type` | SLA扣款、折扣、退款等，可为空 |
| 解释 | `variance_reason` | 延期、争议、未验收、发票退回等 |

### 4.3 投影粒度

- 周期性收费：一个合同项的一个账期形成一个事件。
- 阶段性收费：一个计费规则或里程碑形成一个事件。
- 一次性收费：一个一次性计费规则形成一个事件。
- 订单收费：事件必须归属订单，再归属合同项。
- 调整：必须关联被调整的应收事件；不允许只在合同层悬空展示。

## 5. 指标口径

### 5.1 顶部六张金额卡片

| 指标 | 计算口径 |
| --- | --- |
| 合同金额 | 非框架合同取合同有效版本约定总额；框架合同显示框架上限并明确标注“额度” |
| 已形成应收 | 已确认且未作废的应收明细净额合计 |
| 未到应收 | 当前计划中尚未形成应收、且预计日期未早于今天的金额；待触发金额单独标记不确定性 |
| 已开票 | 有效发票映射金额合计 |
| 已收款 | 有效回款分配到本合同应收明细的金额合计 |
| 逾期未收 | 对每个到期事件分别计算 `max(应收净额 - 有效回款分配, 0)`，仅汇总 `due_date < today` 的事件 |

补充规则：

- 草稿应收不计入“已形成应收”，可以计入当前计划。
- 已作废应收不进入任何执行金额，但保留在审计明细中。
- 未分配回款不计入合同“已收款”。
- 框架合同的剩余额度不是未到应收。
- 合同总额为空或可变时，不展示具有误导性的合同完成率。
- 金额差异不得被静默截断；出现负数或超额映射时展示数据异常状态。

### 5.2 比率

| 指标 | 分子 | 分母 |
| --- | --- | --- |
| 应收形成进度 | 已形成应收 | 可确定的当前计划金额 |
| 合同开票进度 | 已开票 | 合同金额或框架已下单金额，必须在标签中说明 |
| 应收开票率 | 已开票 | 已形成应收 |
| 应收回款率 | 已收款 | 已形成应收 |
| 订单额度使用率 | 已下单金额 | 框架合同上限 |

合同层和局部视图不能共用一个含义模糊的“开票率”。周期格子使用“当期应收开票率”，顶部使用“合同开票进度”。

### 5.3 缓存字段策略

`RevenueReceivableBill.invoiced_amount` 和 `receipted_amount` 暂时保留，但展示取数应以有效映射和有效分配为准。

后台聚合同时返回：

- `calculated_amount`：根据明细关系实时计算。
- `cached_amount`：账单缓存值。
- `reconciliation_status`：一致、不一致、待刷新。

发现不一致时，在详情页展示数据质量提醒，禁止用一个页面显示缓存金额、另一个页面显示实时金额而不作解释。

## 6. 页面信息架构

### 6.1 第一层：合同总览

页面首屏包含：

1. 合同名称、编号、客户、合同类型、状态、期间和负责人。
2. 六张金额卡片。
3. 不确定应收、数据质量异常和高风险事件提示。
4. 合同整体执行链：合同/订单 → 履约或计费 → 应收确认 → 开票 → 收款 → 经营核销。

执行链每个节点显示金额和完成比例。无可靠分母时显示金额，不显示百分比。

### 6.2 第二层：综合应收时间轴

统一按 `current_planned_date`、`due_date`、触发条件排序：

- 虚线标记原计划。
- 实线标记当前计划。
- 圆点标记实际发生。
- 没有日期的条件型事件放入“待触发”区，不混入确定现金流。
- 支持筛选逾期、未来30天、未来90天和待触发。

### 6.3 第三层：类型专属主视图

#### 周期账单矩阵

- 行：收费项目，必要时按订单或项目分组。
- 列：月份或季度。
- 单元格：当期净应收和状态。
- 点击单元格打开事件抽屉。
- 支持水平滚动、年份切换和只看异常。

统一状态：

| 颜色 | 状态 |
| --- | --- |
| 绿色 | 已全部收款 |
| 蓝色 | 已开票且未到期 |
| 黄色 | 部分回款或即将到期 |
| 红色 | 逾期未收 |
| 灰色空心 | 未来计划 |
| 灰色横线 | 本周期不计费 |

#### 里程碑时间线

每个节点展示：

- 触发条件及前置条件。
- 原计划、当前计划和实际日期。
- 原计划金额、当前计划金额和已形成应收。
- 已开票、已收款和逾期天数。
- 差异原因。

#### 订单泳道

- 第一层显示框架上限、已下单、已形成应收、已收款和剩余额度。
- 每个订单一条泳道。
- 泳道内展示订单期间、计费、应收、开票和回款事件。
- 支持按订单状态和项目筛选。

关系必须保持：框架合同 → 订单/开工单 → 合同项 → 计费规则 → 应收事件。

#### 混合合同多泳道

默认按收费计划分组，可切换：

- 按收费项目。
- 按订单。
- 按应收月份。

周期事件以连续单元格展示，阶段事件以节点展示，调整事件以增减标记展示。

### 6.4 关联抽屉

点击任何事件后打开统一抽屉，展示：

1. 计费期间或里程碑。
2. 触发条件和日期变化。
3. 原计划、当前计划、实际应收。
4. 应收账单和应收明细。
5. 发票明细及映射金额。
6. 回款流水及分配金额。
7. 调整和差异原因。
8. 数据质量与金额闭合结果。

抽屉只负责解释一笔事件，不把全部合同数据一次性展开。

### 6.5 明细表

明细表按统一应收事件展示，支持：

- 合同项、项目、订单、账期、状态和风险筛选。
- 原计划、当前计划、应收、开票、回款和调整金额列。
- 逾期天数和差异原因列。
- 导出当前筛选结果。
- 跳转到应收账单、发票和回款对象。

## 7. 现有模型差距

### 7.1 必须补齐

#### 应收计划兼容边界（2026-07 决策）

本系统定位为财务系统之外的企业运营数据附加系统，应收计划不再作为合同运营主流程的必填对象。当前主流程统一为：

> 合同项 → 计费规则 → 账期或已确认业务触发 → 应收明细 → 发票与回款事实

周期规则直接形成未来账期投影；阶段性和一次性规则在没有可靠触发事实时只显示“待触发”，不得使用合同生效日等字段推断虚假日期。业务事件确认后，触发记录直接关联计费规则，并按规则配置的偏移天数计算应收形成日。

既有应收计划、计划版本及其 CRUD、迁移和历史关联继续保留，用于兼容存量数据或未来确有预算版本管理需求的场景，但不出现在主导航、合同详情主操作和综合时间轴的数据依赖中。

#### 历史方案：计划版本

现有合同版本只能说明合同版本有效期，不能记录单个应收事件的原计划与当前计划。建议增加应收计划及计划版本结构，至少记录：

- 计划金额。
- 计划触发方式。
- 计划日期或触发后偏移天数。
- 生效版本。
- 变更原因。
- 是否为当前版本。

#### 条件触发

`RevenueBillingRule.trigger_event` 当前只有事件类型，缺少：

- 触发后账期天数。
- 原计划触发日期。
- 当前预计触发日期。
- 实际触发日期。
- 前置条件状态。

#### 订单/开工单

`RevenueContractLine.order_id` 只能作为外部引用。订单泳道至少需要独立订单实体，记录订单编号、项目、金额、业务期间、状态、来源系统和外部ID。

实施状态（2026-07-14）：已新增 `RevenueOrder` 订单/开工单实体，并通过 `RevenueContractLine.revenue_order` 建立直接关联。迁移会按“合同 + 项目 + 原订单号”归并历史 `order_id`，保留原字段用于核对；订单泳道优先使用订单事实金额，未迁移字符串继续作为兼容数据并明确标记。

#### 调整解释

如果页面必须解释 SLA 扣款、折扣、退款等事项，需要增加调整记录或事件。它应关联应收计划或应收明细，并保存类型、金额、日期、原因、来源和状态。

### 7.2 可以沿用

- `RevenueContract`：合同主数据和合同类型。
- `RevenueContractVersion`：合同法律/商务版本。
- `RevenueContractLine`：收费项目。
- `RevenueBillingRule`：周期、阶段和一次性规则分类。
- `RevenueBillingSegment`：计费计算快照。
- `RevenueReceivableBill/Line`：已形成应收事实。
- `RevenueInvoiceMapping`：开票事实。
- `RevenueReceiptAllocation`：合同侧收款及经营核销事实。

## 8. 兼容和迁移策略

1. 第一阶段不删除任何现有收入模型和字段。
2. 新投影服务同时支持旧数据和新增计划数据。
3. 缺少计划版本的旧数据使用“仅有实际数据”状态，不反推虚假的原计划。
4. 现有 `order_id` 可在迁移期映射为订单外部编号；无法匹配时归入“未建档订单”。
5. 现有 `adjusted_amount` 继续参与净额计算，但无调整记录时显示“调整原因未记录”。
6. 原三套页面在新详情页稳定前保留路由，但不继续扩展；验收后再重定向或移除。

## 9. 后端组织建议

避免继续把所有聚合逻辑堆入 `views.py`。建议拆分为：

- `services/revenue_events.py`：构建统一应收事件。
- `services/revenue_metrics.py`：合同、订单和事件指标。
- `services/revenue_views.py`：周期矩阵、时间线和泳道视图模型。
- `selectors/revenue_contracts.py`：集中处理查询和预取。

模板只消费准备好的视图模型，不在模板中计算金额或判断复杂状态。

## 10. 测试要求

### 10.1 指标口径

- 草稿、确认和作废应收的汇总边界。
- 未分配回款不进入合同已收款。
- 映射和分配状态只统计有效记录。
- 单笔逾期金额逐事件计算，不能按月份粗略判断。
- 框架剩余额度不计入未到应收。
- 缓存金额与实时金额不一致时产生对账告警。

### 10.2 日期和状态

- 固定日期事件。
- 条件已确定但日期未知的事件。
- 当前预计日期发生变化。
- 实际触发早于或晚于计划。
- 已开票未到期、部分回款、逾期和结清状态。

### 10.3 类型视图

- 周期矩阵按合同项和账期正确落格。
- 阶段时间线不使用合同项生效日伪造计划日期。
- 框架合同按订单分组并正确计算额度。
- 混合合同同时包含周期和阶段事件。
- 抽屉链路金额闭合。

## 11. 分阶段实施

### 阶段一：统一口径和事件投影

- 建立统一聚合服务。
- 修正逾期口径。
- 统一顶部与明细金额来源。
- 增加对账异常提示。
- 保持现有页面结构，降低第一阶段风险。

### 阶段二：统一详情页骨架

- 合并三套详情模板。
- 完成顶部卡片、执行链、综合时间轴、关联抽屉和明细表。
- 建立合同类型到主视图的路由规则。

### 阶段三：类型专属视图

- 优先实现周期账单矩阵。
- 实现完整里程碑时间线。
- 增加订单实体后实现订单泳道。
- 最后实现混合合同多泳道。

### 阶段四：规则触发与调整能力

- 计费规则覆盖周期、阶段和一次性收费。
- 业务触发记录直接关联计费规则。
- 增加调整解释数据。
- 综合时间轴展示规则预测与财务实际；应收计划仅保留历史兼容。

### 阶段五：公司级总览

- 未来7天、30天、90天应收时间带。
- 按月预计应收堆叠图。
- 待触发和日期不确定金额单独展示。

## 12. 第一轮开发建议范围

第一轮建议只实施阶段一和阶段二的基础部分：

1. 提取统一事件及指标服务。
2. 修正顶部六项金额和逾期计算。
3. 消除缓存金额与实时映射金额混用。
4. 合并三套详情页入口。
5. 保留现有阶段时间线和月度日历作为过渡组件。
6. 为周期矩阵、订单泳道和规则触发记录预留稳定的数据接口。

这样可以先解决口径和维护性问题，再增加复杂交互，避免在不稳定的数据定义上重做界面。
